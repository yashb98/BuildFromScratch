## 2. §C25 — Per-Stage Eval-Completeness Gate (paste-ready contract section)

> ### §C25 — Per-Stage Eval-Completeness Gate
>
> **§C25.0 Purpose.** No lifecycle-stage *headline* may be marked `done`/`win`, and no claim may reach a README/manuscript, unless the **required eval battery for that run's lifecycle stage** has actually run and is recorded. This is the durable fix for the pretraining three-build headline (28.65/23.52/29.54) shipped on n=1 FineWeb val PPL with no downstream, no seed CI, no contamination performance-check. The gate is *completeness* (did the stage-required battery run?), layered on top of the existing *significance* gates (§C10 comparability, §C13 ablation objective, §C17 seed-CI, §C18 iso-FLOP, §C21 distributed-correctness).
>
> **§C25.1 Every run carries its lifecycle stage.** The ledger run entry gains an additive key (`ledger.py` only, never hand-edited, §C11):
> `lifecycle_stage ∈ {data, architecture, scaling, pretrain-run, mid-training, base-eval, sft, preference, rlvr, safety, interpretability, systems, serving}`.
> A run with no `lifecycle_stage` is treated as `unknown` → cannot be `win` (only `inconclusive`). The stage is set at launch by the launching skill (ablation-runner/post-train/remote-launcher) from the brief's objective (§C13) and run_type.
>
> **§C25.2 The required-battery registry.** Each stage maps to its **STAGE-DONE minimal battery** (the final column of the §C25 matrix in `research/eval_completeness_registry.md`, suite-version-stamped per §C10). The registry is the single source of truth; it lists, per stage, the **required** items (HARD), the **report-only** items (must appear or be marked `not run — <reason>`), and the **propose-only** items (named, never silently omitted). Editing the registry bumps a `registry_version` stamp.
>
> **§C25.3 Where it plugs in (S8, the verdict).** The verdict owner is **ablation-runner Phase 6** (the §C11 launch monopoly's judge), which already calls `/eval-harness` and writes `verdict`. §C25 inserts a **completeness check between metric-collection and verdict**:
> 1. eval-harness measures + stamps `suite_version` (unchanged; it never judges).
> 2. ablation-runner Phase 6 loads the run's `lifecycle_stage`, looks up the registry battery, and checks every HARD item is present in the run's recorded metrics/artifacts.

## 3. The Recency Rule (contract-grade)

> ### §C25.7 — Benchmark Recency Rule
> **§C25.7.1** Every stage battery in `eval_completeness_registry.md` carries a `researched_on` date and a per-item `fetch_verified ∈ {true,false}` flag. `fetch_verified=true` ONLY if the source page/PDF was actually retrieved this session; search-index-only items are `false` and may NEVER be the **sole** signal for a gate.
> **§C25.7.2 Re-validation window.** A stage's benchmark set is re-validated (re-researched current-date-back) if `researched_on` is older than **120 days**, OR immediately when a run for that stage is launched and a newer dated benchmark exists in `community-pulse`/`model-radar`. Re-validation is a `/ml-research`-style dated pass, not a memory recall.
> **§C25.7.3 Stale/saturated disallow-list (sole-signal ban).** The following may NEVER be a stage's sole headline signal and are auto-flagged if presented as a frontier metric: raw MMLU; HumanEval-alone; HellaSwag-as-headline; GSM8K-original as a clean absolute; GLUE/SuperGLUE; any single-number leaderboard rank; raw (non-length-controlled) AlpacaEval; raw throughput with no SLO; datasheet/sparse/FP4 peak in an MFU denominator; nvidia-smi GPU-util% as efficiency; raw single-needle NIAH as a long-context headline; advertised context window as a capability; n-gram-only decontamination presented as sufficient; fertility-only tokenizer judgement; **any val-PPL n=1 stage headline** (the founding mistake).
> **§C25.7.4 Explicit-rejection record.** When a stale benchmark is rejected for a stage, the registry records *why* (saturated / contaminated / superseded-by-X) so the rejection is auditable, not silent.
